## Objetivo e versão

Validar o disparo e a consulta de uma rodada para portas ativas (RF07), o horizonte padrão e as entradas da predição (RF08), conforme os [requisitos](/sprints/sprint-3/requisitos/). Esta entrega complementa as lacunas L01/L05 do [mapeamento inicial](/sprints/sprint-5/mapeamento-testes-rf/).

**Data:** 05/10/2026. **Commit base:** `545cd269778aefd2752cfb793302ac289e205962`. A execução inclui as alterações locais desta task. O [arquivo de evidências](/evidencias/rf07-rf08.json) contém hashes dos arquivos testados, resultados iniciais e finais e os testes ignorados.

## Implementação e limites da arquitetura testada

O arquivo `src/backend/tests/integration/prediction_requirements_test.go` exercita middleware JWT, handler, casos de uso e **cliente HTTP de ML reais**. Um servidor local `httptest` representa o serviço de inferência. O repositório e a unidade de trabalho são substitutos em memória; não comprovam transações SQL.

O conjunto contém duas portas ativas — FAL/P1/4 e PIN/P2/8 — e uma inativa — FAL/P1/5. O repositório em memória fornece apenas as ativas. O servidor verifica a chamada `POST /v1/predictions`, o tipo JSON e as identidades enviadas; responde com versão `rf-test-v1` e probabilidades 0,8 e 0,2. O fluxo verifica associação das previsões, ID da rodada, quantidade de portas, uma inspeção automática e consulta posterior idêntica à criação.

A seleção SQL real tem um teste separado, `TestRF07_PostgresActiveDoorSelection`. Ele chama `PostgresPredictionRepository.ListDoorsForInference` usando tabelas temporárias de portas/estações dentro de uma transação revertida ao final. As tabelas temporárias substituem as tabelas da aplicação somente nessa conexão. O cenário não exige migrations e não valida o esquema completo. **Foi ignorado nesta execução por ausência de `TEST_DATABASE_URL`.** Docker também estava sem daemon disponível.

O serviço Python, o artefato de ML, a construção de features a partir dos históricos e o navegador não foram executados. A comunicação HTTP testada utiliza resposta controlada, sem avaliar qualidade preditiva.

## Falha encontrada e correção

O handler descartava o erro de `ShouldBindJSON`. Assim, mesmo JSON malformado ou `horizon_days` em formato inválido iniciava uma rodada. Zero e valores negativos também eram silenciosamente transformados em sete pelo caso de uso.

A primeira execução confirmou falha nos cinco subcasos HOR-03/HOR-04. O handler agora:

- Retorna HTTP 400 quando o JSON ou o tipo do horizonte é inválido.
- Distingue campo ausente de zero explícito usando `*int`.
- Rejeita zero e negativos antes de chamar o caso de uso.
- Usa sete quando não há valor informado; preserva corpo vazio e `null` como ausência.

A alteração está em `src/backend/internal/adapter/http/dashboard_handler.go`. O contrato em `src/backend/docs/openapi.json` registra os erros e a limitação vigente. A validação de positividade cobre a entrada HTTP; não altera o comportamento dos chamadores internos do caso de uso.

## Divergência do RF08

O requisito solicita horizonte configurável com padrão de sete dias. Entretanto:

1. `TriggerPredictionsUseCase.execute` sobrescreve `horizonDays` com sete.
2. `port.MLClient.PredictBatch` e o corpo enviado pelo cliente HTTP recebem apenas portas, sem horizonte.
3. `PredictUseCase.execute` do serviço Python também recebe apenas portas. O fluxo de treinamento registra `evaluation_horizon_days: 7`.
4. A especificação OpenAPI limita o valor suportado a sete; valores positivos diferentes ainda são aceitos e sobrescritos em execução, comportamento registrado por HOR-02.

**RF08 não está plenamente atendido.** Alterar somente o número salvo na rodada não comprovaria que o modelo passou a prever outro intervalo. A resolução exige implementar suporte coerente no modelo/contrato, backend e interface, ou revisar formalmente o requisito. Esta task não modifica o horizonte do modelo nem considera a substituição silenciosa como atendimento do requisito.

## Reprodução

Ambiente utilizado: **Go 1.26.0, Windows amd64**. Na pasta `src/backend`, executar os novos cenários:

```sh
go test -count=1 -json ./tests/integration -run '^TestRF0[78]_' > prediction-results.json
```

Para repetir a regressão realizada:

```sh
go test -count=1 -json ./tests/... ./cmd/api > prediction-regression.json
```

Para o teste SQL, fornecer `TEST_DATABASE_URL` de um PostgreSQL de teste com permissão de criar tabelas temporárias. Exemplo em PowerShell, substituindo as credenciais locais:

```powershell
$env:TEST_DATABASE_URL = 'postgres://usuario:senha@localhost:5432/banco_de_testes?sslmode=disable'
go test -count=1 -v ./tests/integration -run '^TestRF07_PostgresActiveDoorSelection$'
```

O teste SQL falha se a variável estiver configurada e a conexão ou consulta falhar; a ausência da variável produz `skip`. Os demais testes dessa task não precisam de banco nem credenciais externas. A regressão completa contém outros testes de banco com seus próprios procedimentos; usar somente banco isolado de teste.
