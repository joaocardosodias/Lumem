## Cobertura adicionada

O teste anterior `TestIntegration_CompleteOperationalPipeline` exercita a sequência operacional, mas usa um roteador de teste que deixa várias rotas públicas e um cliente de ML substituto chamado diretamente. Esta entrega adiciona:

- `src/backend/tests/integration/authenticated_workflow_test.go`: login com bcrypt e JWT reais; chamadas por `http.Client` a um servidor local; rotas protegidas; importação em fila controlada; cliente HTTP real de ML; falhas e recuperação no mesmo fluxo.
- `src/backend/cmd/api/workflow_routes_test.go`: usa `buildRouter`/`registerRoutes` da aplicação para verificar autorização do disparo de predição em configuração `production` e `development`.
- Diagrama SVG e este relatório. Não houve alteração de código de produção nesta task.

O fluxo principal monta um roteador de teste com proteção equivalente nas rotas usadas. O teste separado de permissões verifica o registro real da aplicação, sem substituí-lo por uma cópia. O papel de engenharia segue o identificador existente no sistema, **`enginner`**.

## Componentes reais e substituídos

| Camada | Execução desta task | Limite da evidência |

| Login, JWT e autorização | Handler e caso de uso reais; senha de teste verificada com bcrypt; token usado nas chamadas seguintes. | Usuários em repositório de memória. Não valida banco de usuários. |

| Persistência e consultas | Repositórios em memória compartilhados pelas etapas. | Sem PostgreSQL, constraints, agregação SQL, transações ou durabilidade entre processos. |
| Rotas da aplicação | Permissão verificada com `buildRouter`/`registerRoutes` reais. | Nesse teste separado, ML e persistência são substitutos em memória. |

O dashboard e a linha do tempo do fluxo usam os substitutos existentes do repositório. Eles permitem verificar a passagem dos dados entre etapas, mas não comprovam os filtros e joins do PostgreSQL. O substituto de linha do tempo retorna a coleção de manutenções do teste; não foi utilizado para afirmar isolamento de manutenções por porta.

## Sequência operacional verificada

1. Acesso ao dashboard sem token retorna **401**. Login de operador e engenharia retorna tokens utilizáveis.
2. Operador tenta disparar predição e recebe **403**, sem chamada ao ML.
3. Operador importa dois alarmes e duas manutenções ZM01 em CSV. Antes de processar o job, o status é `processing`, sem linhas inseridas; depois, `completed`, com duas linhas processadas/inseridas por arquivo. Arquivo temporário é removido.
4. Reenvio do mesmo conteúdo retorna **409**, sem enfileirar outro job.
5. Cadastro manual de manutenção retorna **201**, ID e origem `manual_form`. A consulta reúne as duas manutenções importadas e a manual, totalizando três.
6. Engenharia inicia a predição. O servidor ML recebe exatamente FAL/P1/4 e PIN/P2/8 e responde com probabilidades 0,8 e 0,2. A API retorna duas portas avaliadas, uma em risco e horizonte de sete dias. A consulta da última rodada é idêntica à resposta de criação.
7. Uma inspeção pendente é gerada para FAL/P1/4, ligada ao ID da previsão em risco. O operador passa a inspeção para `in_progress` e depois `completed`; a conclusão passa a ter data.
8. O dashboard retorna duas portas, uma em risco, zero inspeções pendentes, uma concluída e FAL como estação crítica com uma porta em risco. A linha do tempo confirma o alarme importado, a classificação de risco e a inspeção concluída.

Os históricos importados ficam disponíveis na mesma base controlada, mas **não alimentam um modelo real nesta execução**: o serviço de ML simulado recebe apenas as identidades das portas e fornece probabilidades fixas.

## Reprodução

Ambiente: **Go 1.26.0, Windows amd64; Node 22.15.0**. Os cenários novos usam somente serviços locais temporários e dados de teste.

Na pasta `src/backend`, para os novos cenários:

```sh
go test -count=1 -json ./tests/integration ./cmd/api -run '^TestRFIntegration_' > workflow-results.json
```

Para repetir a regressão realizada:

```sh
go test -count=1 -json ./tests/... ./cmd/api ./internal/usecase > workflow-regression.json
```

Na pasta `src/frontend`:

```sh
npm test
```

Verificar código de saída e eventos `pass`, `fail` e `skip`. Não publicar tokens ou credenciais em evidências; o artefato desta task armazena resultados dos testes, sem respostas de login.

## Validação completa ainda pendente

**Execução posterior:** os cinco testes PostgreSQL listados acima já passaram na [validação de PostgreSQL e regressão completa](/sprints/sprint-5/validacao-postgresql-regressao-completa/), que também executou todos os pacotes Go. Os resultados desta página permanecem como registro da task RF [8].

A sequência local aumenta a cobertura das integrações internas, mas a lacuna L09 permanece parcialmente aberta. Para fechar a validação com infraestrutura real:

1. Preparar ambiente isolado com PostgreSQL, migrations, storage configurado, River/worker, serviço Python com artefato compatível e frontend conectado à API. Registrar versões e hashes do modelo, sem usar credenciais ou dados operacionais reais nas evidências.
2. Repetir o roteiro FLX-01 no navegador, usando os dois perfis, e aguardar o processamento assíncrono pelo worker. Conferir os registros efetivamente persistidos, sem acionar `ProcessJob` manualmente.
3. Confirmar a construção das features a partir dos históricos importados e a identidade dos resultados retornados pelo modelo. Testar repetição de rodada, prevenção de inspeções abertas duplicadas e comportamento transacional.
4. Repetir falha/recuperação do serviço de ML e do worker; verificar feedback da interface e ausência de perda ou duplicação dos dados.
5. Registrar resultados por etapa, capturas da interface, logs com IDs de correlação e os testes SQL executados. Diferenciar esse registro dos testes com substitutos desta entrega.

As divergências já documentadas continuam abertas: horizonte configurável do RF08, prioridade explícita das inspeções no RF11 e demais limites registrados nas tasks anteriores. A aprovação do fluxo com probabilidades fixas não comprova qualidade preditiva sobre históricos reais nem resolve essas divergências.
