Esta documentação inicia a validação dos **critérios de funcionamento** da plataforma Lumem na Sprint 5. O objetivo é verificar se os componentes entregues funcionam de forma integrada e se o sistema pode ser demonstrado de maneira reproduzível, desde a abertura da interface até a execução de uma previsão.

A análise considera o frontend React, a API em Go, o PostgreSQL e o serviço preditivo em Python. Os serviços de armazenamento de objetos, processamento assíncrono e observabilidade também fazem parte da arquitetura e deverão ser incluídos na validação final.

  <h2 style="position: relative; z-index: 1; color: white; margin: 0;">2. Critérios de avaliação</h2>
</div>

| Critério | Resultado esperado | Evidência mínima |
| :--- | :--- | :--- |
| **Inicialização** | Os serviços necessários iniciam sem erro impeditivo. | Estado dos contêineres e logs de inicialização. |
| **Disponibilidade** | Interface, API e serviço de ML respondem pelos endereços configurados. | Resposta HTTP dos healthchecks e carregamento da interface. |
| **Autenticação** | Um usuário cadastrado consegue entrar e acessar somente as funções permitidas ao seu papel. | Login válido, consulta do usuário autenticado e teste de autorização por perfil. |
| **Dashboard** | Os indicadores são carregados a partir da API sem dados estáticos utilizados como resultado operacional. | Resposta do resumo do dashboard e conferência visual dos valores. |
| **Predição** | O backend aciona o modelo, recebe probabilidades e persiste uma rodada oficial. | Código HTTP `201`, identificador da rodada e quantidade de portas avaliadas. |
| **Persistência** | Dados permanecem disponíveis após reinício controlado. | Reinício dos serviços e nova consulta aos registros. |
| **Ingestão** | Arquivos aceitos são processados pelo worker, com estado final e tratamento de falhas. | Upload de teste, acompanhamento do status e registros no banco. |
| **Observabilidade** | Logs, métricas e traces permitem acompanhar uma operação entre os serviços. | Consulta no Grafana e correlação por identificador de requisição ou trace. |
| **Reprodutibilidade** | Outra pessoa consegue preparar e executar o projeto seguindo a documentação. | Execução do roteiro documentado em ambiente limpo. |

Um critério será considerado **atendido** quando houver evidência reproduzível do comportamento esperado. Ele será classificado como **parcial** quando apenas parte do fluxo tiver sido verificada e como **pendente** quando ainda não houver evidência suficiente.

A primeira verificação integrada foi realizada em **4 de outubro de 2026**, em ambiente local, com os seguintes componentes:

- frontend React servido por Nginx;
- API Go com migrações automáticas;
- PostgreSQL 16 local;
- serviço de Machine Learning com o Modelo 5, versão `v1.0.0`;
- proxy Nginx expondo a aplicação em `http://localhost`.

O armazenamento de uploads foi configurado no modo local durante essa verificação. Essa escolha permitiu validar a interface, a API, o banco e a inferência sem alterar a arquitetura oficial documentada para o projeto.

| Prontidão do modelo | O endpoint `/health/ready` respondeu `HTTP 200`, com a versão `v1.0.0` carregada. | Atendido |
| Login | A API de autenticação respondeu `HTTP 200` e retornou um token para usuários locais de teste. | Atendido |
| Sessão autenticada | A rota `/api/v1/auth/me` respondeu `HTTP 200` com identificação e papel do usuário. | Atendido |
| Resumo operacional | A rota `/api/v1/dashboard/summary` respondeu `HTTP 200` com os indicadores esperados. | Atendido |
| Execução preditiva | O disparo oficial respondeu `HTTP 201`, criou uma rodada e avaliou **528 portas**. | Atendido |
| Build da documentação | O portal Astro foi compilado com sucesso. | Atendido |

Os números acima descrevem a execução indicada e não representam garantia de disponibilidade ou desempenho em produção. As credenciais usadas na validação são locais e não devem ser publicadas na documentação.

Para concluir os critérios de funcionamento, o grupo deverá:

1. revisar as referências das imagens do MinIO e confirmar a subida pelo Docker Compose oficial;
2. executar os testes de integração do backend com PostgreSQL;
3. validar permissões de operador e engenharia em todas as rotas restritas;
4. registrar um upload de alarmes e de manutenção, incluindo processamento, sucesso e falha;
5. reiniciar os serviços e confirmar a persistência de usuários, predições e registros operacionais;
6. verificar logs, métricas e traces no Grafana;
7. repetir o roteiro no ambiente implantado e registrar data, versão, resultado e responsável;
8. anexar capturas ou logs sem senhas, tokens ou dados sensíveis.

A verificação inicial demonstra que o núcleo da solução está funcional: a interface carrega, o backend acessa o banco, a autenticação responde, o dashboard consulta seus indicadores e o serviço preditivo conclui uma rodada com as portas cadastradas. Portanto, há evidência de integração entre as principais camadas do produto.

O funcionamento completo ainda não pode ser considerado encerrado. Permanecem pendentes as evidências de ingestão assíncrona, persistência após reinício, autorização completa por perfil, observabilidade, execução integral pelo Compose e validação no ambiente implantado. Esta página deverá ser atualizada à medida que esses testes forem concluídos.
