Os resultados são comparados por IDs, verificando também a exclusão dos registros que não correspondem.

## Falhas encontradas e correções

A primeira execução dos testes de filtros terminou com 32 aprovações e duas falhas:

1. **Datas futuras em períodos recentes:** `inPeriod` verificava apenas a data inicial. Agora verifica também que a data não ultrapassa o dia atual. O filtro `all` continua sem restrição temporal.
2. **Duração ausente interpretada como zero:** a conversão numérica de `null` ou string vazia produzia zero. Agora esses valores são excluídos quando existe limite de duração; registros com zero informado continuam elegíveis.

Após as correções, os **34 testes do frontend passaram**. A extração das regras também permite buscar em registros com campos opcionais ausentes sem chamar métodos de string em valores indefinidos.

## Reprodução

Ambiente usado: Go 1.26.0 em Windows amd64 e Node 22.15.0. Os testes novos não exigem banco ou credenciais reais.

Na pasta `src/frontend`:

```sh
npm test
npm ci --no-audit --no-fund
npm run lint
npm run build
```

Os testes usam somente módulos nativos do Node e não dependem do `npm ci`; instalação é necessária para lint/build. Para salvar evidência TAP:

```sh
node --test --test-reporter=tap tests/recordFilters.test.js > filters-results.tap
```

Na pasta `src/backend`, para os novos testes:

```sh
go test -count=1 -json ./tests/integration -run '^TestRF0[56]_' > maintenance-filter-results.json
```

A regressão executada incluiu os quatro pacotes abaixo:

```sh
go test -count=1 -json ./tests/unit/usecase ./tests/unit/http ./tests/integration ./cmd/api > maintenance-regression.json
```

Verificar código de saída e eventos `pass`, `fail` e `skip`. O arquivo de evidências guarda os resultados novos dentro dessa regressão. Os testes Go entram na descoberta do pipeline existente; `npm test` foi disponibilizado localmente, sem alteração do pipeline nesta task.

## Situação dos requisitos e pendências

**RF05:** cadastro e consulta validados nos cenários HTTP com persistência em memória, incluindo todos os campos do requisito. Permanecem pendentes navegador, persistência real e regras semânticas adicionais como datas impossíveis ou duração negativa.

**RF06 permanece parcialmente validado.** Os filtros existentes agora têm testes com inclusão/exclusão de registros e combinações. Entretanto:

- Não foi localizado filtro explícito de **prioridade** nas quatro telas. É necessário definir a regra e implementá-la, ou revisar formalmente o requisito; classificar risco ou origem IA não comprova prioridade.
- Predições apresenta filtros de risco, estação, plataforma e busca, mas não período. Manutenção e inspeções possuem filtros temporais no frontend. É necessário confirmar quais critérios do RF06 se aplicam a cada tela.
- Os filtros locais operam sobre a coleção carregada. Estes testes não comprovam que todos os registros do banco foram carregados ou que filtros funcionem entre páginas de uma consulta remota.
- A verificação do frontend é de funções usadas pelas páginas, não de renderização, mensagens, navegação ou cliques. A verificação SQL requer PostgreSQL isolado de teste.

Para a validação visual posterior, cadastrar uma manutenção completa, consultá-la após recarregar, aplicar cada combinação da matriz, conferir registros e totais, testar resultado vazio e limpar os filtros. Registrar versão, data e evidências desse roteiro separadamente.
