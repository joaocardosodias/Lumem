## Objetivo e versão

Validar os indicadores operacionais do **RF10** e a geração de inspeções ligadas a portas em risco do **RF11**, conforme os [requisitos](/sprints/sprint-3/requisitos/). A entrega complementa as lacunas L06/L08 do [mapeamento](/sprints/sprint-5/mapeamento-testes-rf/).

**Data:** 05/10/2026. **Commit base:** `e4fe84de41eb3e99f1e0a8fb3eb2a38eb91a3a51`. Os testes incluem as alterações locais desta task. O [arquivo de evidências](/evidencias/rf10-rf11.json) contém resultados antes/depois, regressão, saída do frontend e hashes dos arquivos utilizados.

## Falha encontrada e correção

`PostgresDashboardRepository.GetSummary` ignorava erros nas consultas de portas em risco, inspeções pendentes e concluídas. Também ignorava erros de consulta, conversão e iteração do ranking. Nesses casos, podia devolver HTTP 200 com zeros ou um ranking incompleto.

A execução inicial confirmou **seis subcasos com falha**. O erro da primeira consulta, de portas ativas, já era propagado corretamente.

O repositório agora interrompe a operação e retorna o erro em qualquer uma dessas falhas. O fluxo HTTP já converte erros de repositório em HTTP 500. A ausência de uma rodada, representada por `sql.ErrNoRows` na consulta da última predição, continua válida e resulta em zero portas em risco. As regras de contagem e a ordenação SQL não foram alteradas.

No frontend, a extração para `dashboardHighlights` preserva o comportamento existente e permite executar diretamente as regras usadas pelo componente. Não foi introduzida uma nova regra de prioridade.

## Reprodução

Ambiente: **Go 1.26.0, Windows amd64; Node 22.15.0**. Na pasta `src/backend`:

```sh
go test -count=1 -json ./tests/unit/adapter ./tests/integration -run '^TestRF1[01]_' > dashboard-results.json
go test -count=1 -json ./tests/... ./cmd/api ./internal/usecase > dashboard-regression.json
```

Na pasta `src/frontend`:

```sh
npm test
npm run lint
npm run build
```

Para executar a agregação SQL e a prevenção de duplicatas, configurar um PostgreSQL de teste e executar somente o cenário preparado, na pasta `src/backend`:

```powershell
$env:TEST_DATABASE_URL = 'postgres://usuario:senha@localhost:5432/banco_de_testes?sslmode=disable'
go test -count=1 -v ./tests/integration -run '^TestRF10_PostgresIndicatorsAndInspectionDeduplication$'
```

O cenário usa tabelas temporárias dentro de uma transação revertida ao final, com timeout de 30 segundos. Elas substituem as tabelas da aplicação apenas nessa conexão. O usuário do banco precisa de permissão para tabelas temporárias. O cenário não depende de migrations e não comprova constraints do esquema completo, concorrência ou rollback da unidade de trabalho de produção. Variável ausente produz `skip`; conexão ou SQL inválidos com a variável configurada produzem falha.

## Situação de RF10/RF11

**RF10 parcialmente validado:** contrato dos indicadores, tratamento de falhas e regras do ranking no frontend estão testados. A agregação sobre uma base PostgreSQL controlada tem cenário preparado, ainda não executado. A correspondência visual dos cards com a API também permanece pendente.

**RF11 parcialmente validado:** a geração automática, o vínculo com a previsão, o ciclo da inspeção e a seleção de portas em risco para destaque estão testados com os substitutos descritos. Permanecem abertos:

- **Prioridade explícita:** não foi localizado campo de prioridade nem ordenação de inspeções por criticidade. O repositório lista por `created_at DESC`; origem IA e status não comprovam prioridade. É necessário definir e implementar a regra ou revisar formalmente o requisito.
- **Destaque visual:** os testes verificam os dados destinados ao painel, sem validar badges, cores, navegação ou acessibilidade no navegador. As cinco portas exibidas seguem a ordem recebida, sem ordenação adicional por probabilidade.
- **Duplicatas e transações reais:** executar o cenário PostgreSQL e validar concorrência/rollback com a infraestrutura real. O repositório em memória usado no ciclo HTTP não implementa a restrição de duplicatas.
- **Rodadas repetidas:** a implementação SQL preserva o vínculo da inspeção aberta com a previsão original ao reutilizá-la. O teste preparado registra esse comportamento; o requisito não define se uma nova rodada deve atualizar esse vínculo.

Os resultados não comprovam integração completa com modelo de ML, dados históricos e banco operacional reais.
