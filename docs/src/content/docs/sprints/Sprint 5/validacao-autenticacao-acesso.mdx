## Objetivo

Validar o login por e-mail e senha (RF01) e a restrição dos recursos protegidos a usuários autenticados (RF02), complementando o [mapeamento de cobertura](/sprints/sprint-5/mapeamento-testes-rf/).

Data: 05/10/2026. Versão dos testes: commit `8a41c4add2fec4929b98c4ebda4e92d97c3ebfd0`. As evidências de execução foram acrescentadas posteriormente à documentação.

## Implementação dos testes

Os caminhos são relativos à raiz do repositório.

| Arquivo | Responsabilidade |
| --- | --- |
| `src/backend/tests/integration/auth_requirements_test.go` | `TestRF01_LoginContract`: login pelo handler HTTP com caso de uso, bcrypt e JWT reais; repositório de usuários em memória. |
| `src/backend/tests/integration/api_test.go` | Fixture compartilhada de autenticação; permite configurar usuário ativo ou inativo. Mantém a fixture anterior para os testes existentes. |
| `src/backend/cmd/api/auth_requirements_test.go` | `TestRF02_AllProtectedRoutesRejectUnauthorizedAccess`: percorre as rotas do router real em configuração de produção e desenvolvimento e verifica quatro formas de acesso não autorizado. |
| `src/backend/tests/unit/http/health_test.go` | Ajuste da fixture de armazenamento temporário para Windows e Unix, identificado na regressão: usa diretório inexistente dentro de `t.TempDir()` e configura `TMPDIR`, `TMP` e `TEMP`. |

Os novos testes usam as implementações existentes. Não alteram a lógica de autenticação nem os requisitos. As suítes anteriores de login, middleware e controle de papel também fazem parte da validação.

O teste de rotas considera todo caminho `/api/v1/` protegido, exceto `/api/v1/auth/login`. Essa regra deve ser revisada explicitamente se surgir uma nova API pública. A enumeração inclui rotas de alarmes, uploads, manutenção, inspeções, predições, dashboard e MLOps; parâmetros de caminho recebem valores de teste. O log informa a quantidade de rotas verificadas.

Os handlers desse teste têm dependências de negócio ausentes: se a autenticação permitir indevidamente chegar a eles, uma falha ou resposta diferente de 401 reprovará o caso. O teste confere também o código de erro e os campos da resposta. Acesso bem-sucedido é validado no fluxo AUT-01.

## Como reproduzir

Pré-requisitos: Go 1.26 ou compatível com `src/backend/go.mod` e dependências Go disponíveis. Esta seleção não requer PostgreSQL, serviço de modelo, credenciais reais nem servidor externo. As contas e chaves usadas nos testes são fictícias.

Na pasta `src/backend`, executar:

```sh
go test -count=1 -json ./tests/unit/usecase ./tests/unit/http ./tests/integration ./cmd/api -run '^(TestLoginUseCase_.*|TestAuthHandler_Login|TestAuthMiddleware_.*|TestRequireRole_.*|TestIntegration_FullAuthFlow|TestRF01_LoginContract|TestRF02_AllProtectedRoutesRejectUnauthorizedAccess)$' > auth-rf-results.json
```

`-count=1` impede reutilização do cache de resultados. O filtro evita os testes de banco do pacote de integração. Verificar o código de saída e os eventos `pass`, `fail` e `skip` do JSON; um caso ignorado não conta como aprovado.

Para regressão dos pacotes unitários e do router:

```sh
go test -count=1 ./tests/unit/usecase ./tests/unit/http ./cmd/api
```

O pipeline existente em `.gitlab-ci.yml` já descobre arquivos `*_test.go` com `go test -race ... ./...`; não é necessário adicionar um job para estes casos. A execução local não comprova execução do pipeline remoto.

### Falha encontrada e reteste

Na primeira regressão, `TestHealthHandler_Ready_StorageDown` esperava HTTP 503, mas recebia 200 no Windows. A fixture configurava somente `TMPDIR`, enquanto o diretório temporário usado nesse ambiente depende de `TMP`/`TEMP`. A preparação foi corrigida para as três variáveis, com restauração automática por `t.Setenv`; o handler de produção não foi alterado. A regressão completa dos três pacotes foi repetida e passou.

`TestCheckDatabaseConnection_AndMigrations` permaneceu ignorado porque não havia PostgreSQL disponível na porta 5439. Esse teste não faz parte da seleção de RF01/RF02; sua ausência não foi contada como aprovação.

Não foram executados o detector de corrida (`-race`), o pipeline remoto, a suíte completa do sistema ou testes no navegador. O resultado comprova os cenários automatizados descritos nesta página, dentro dos limites abaixo. A lacuna L02 do mapeamento inicial foi coberta na API quanto a token expirado e enumeração das rotas protegidas.

## Limites da validação e roteiro da interface

Os testes automatizados desta entrega validam os contratos HTTP, a autenticação e o bloqueio das rotas. O repositório de usuários é simulado, e a suíte não exercita o navegador nem o PostgreSQL.

Para complementar a validação visual, executar o roteiro abaixo em ambiente integrado e registrar data, versão, resultado e captura de tela sem credenciais. **Este roteiro permanece não executado nesta entrega.**

1. Abrir a aplicação sem sessão, inclusive por um endereço de página interna: deve exibir o login, sem conteúdo operacional.
2. Informar credenciais incorretas: deve apresentar erro e manter a pessoa fora da aplicação.
3. Enviar campos vazios: deve impedir login e informar os campos necessários.
4. Entrar com usuário ativo e credenciais válidas: deve apresentar a aplicação para o perfil retornado.
5. Encerrar a sessão e tentar voltar à página interna: deve exigir autenticação novamente.
6. Usar uma sessão expirada e solicitar dados protegidos: a API deve retornar 401, e a interface deve descartar a sessão e exibir login.

A aprovação desses cenários visuais e a persistência real dos usuários continuam necessárias para declarar validação integral de RF01/RF02 em todo o sistema.
