Essa documentação fala sobre o pipeline inteiro, de onde vem a predição, como ela atravessa dois sistemas (Go e Python), chega no banco, e como tudo isso é construído e implantado.

Serão explicados quatro camadas, cada uma com um diagrama:

1. **Contexto** — quem/o que participa do sistema
2. **Deploy** — onde cada peça roda fisicamente (containers, VM, rede)
3. **Fluxo de uma predição**, a sequência exata de passos quando alguém dispara uma predição
4. **CI/CD** — como o código vira container rodando em produção

</div>

Passo a passo do que acontece para o operador pedir uma predição e receber a resposta:

1. Operador (ou um agendamento) dispara `POST /api/v1/predictions/trigger` no backend Go.
2. Backend consulta `doors` no Postgres pra saber quais portas estão ativas.
3. Backend monta a lista de portas e manda `POST /predict` pro serviço de ML — só com os identificadores, nenhum dado de telemetria viaja nessa chamada.
4. Serviço de ML busca no Postgres os alarmes recentes (`telemetry_alarms`) e o histórico de manutenção (`maintenance_events`) das estações pedidas.
5. Serviço de ML calcula as features ao vivo (janelas móveis, decaimento, histórico de corretivas) e roda o modelo.
6. Serviço de ML devolve `will_fail` + `probability` por porta.
7. Backend grava a rodada de predições no Postgres e cria uma inspeção automática pra cada porta em risco.
8. Backend devolve a resposta pro operador.

Um .gitlab-ci.yml único cobre os dois lados (Go e Python). Cada mudança passa pelas mesmas sete etapas antes de virar container rodando:

`lint → test → security → build → scan → publish → deploy`

O deploy em si não é automatizado (não existe um estágio que conecte na VM), publicar a imagem no Azure Container Registry é o último passo automático. Depois, o Watchtower (rodando na VM) detecta a imagem nova e reinicia o container sozinho.

  <h2 style="position: relative; z-index: 1; color: white; margin: 0;">6. Validação</h2>
</div>

O pipeline inteiro foi testado de ponta a ponta contra o banco de staging real. Os dois containers (backend e serviço de ML) foram levantados juntos, ligados pela mesma rede, e o fluxo completo (login → trigger → predição → gravação) foi disparado de verdade para 528 portas.

Foi confirmado que:
- `doors.platform` usa o formato `"P1"`/`"P2"`, diferente de `telemetry_alarms.platform` (`"BUT1"`). O serviço de ML já lida com os dois formatos.
- O serviço de ML responde em ~3,3 segundos para 528 portas, dentro do limite de 5 segundos que o cliente Go usa.

Achado de performance: a chamada completa levou ~115 segundos. Isolando a causa: `PostgresPredictionRepository.SaveRun()`, no backend Go, grava as predições uma de cada vez (528 idas ao banco em sequência) em vez de um insert em lote. Isso é uma limitação importante porque pode estourar timeout de proxy em produção.
