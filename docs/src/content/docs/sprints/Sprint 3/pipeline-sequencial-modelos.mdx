# Pipeline Sequencial dos Modelos Preditivos

## 1. Objetivo

O pipeline sequencial combina dois modelos desenvolvidos na Sprint 2 para produzir uma previsão em dois níveis. Primeiro, o **Modelo 7 — CatBoost** identifica quais sistemas de portas de uma plataforma apresentam risco de falha. Depois, o **Modelo 5 — Random Forest** analisa as portas das plataformas sinalizadas para tentar localizar quais delas devem ser priorizadas.

A diferença de granularidade é proposital. O Modelo 7 consegue indicar que **alguma porta da plataforma** poderá falhar, mas não identifica qual delas. O Modelo 5 complementa essa previsão ao estimar o risco de cada porta individual. Portanto, o objetivo não é escolher um modelo vencedor, e sim fazer com que a previsão ampla do primeiro reduza o espaço de busca do segundo.

O fluxo proposto é:

```text
Dados disponíveis na data de referência D
                    ↓
Modelo 7 — CatBoost identifica a plataforma em risco
                    ↓
Plataformas classificadas como risco
                    ↓
Modelo 5 — Random Forest procura a porta em risco
                    ↓
Portas priorizadas para inspeção
```

O Modelo 7 deve ser executado primeiro porque trabalha em um nível mais amplo. O Modelo 5 é executado somente para detalhar o risco das portas pertencentes às plataformas selecionadas na primeira etapa. Essa estratégia é uma **inferência hierárquica em duas etapas**: plataforma primeiro, porta depois.

Esta página registra a construção do pipeline. A Task 1 definiu como os modelos se conectam, a Task 2 preparou o artefato do Modelo 5, a Task 3 implementou o encaminhamento e a Task 4 gerou e avaliou a lista final de portas. A Task 5 incorporou a preparação das features e a execução do CatBoost ao notebook. A Task 6 consolidou a configuração, o reuso dos modelos salvos e o tratamento dos casos sem cobertura. A Task 7 transformou o ranking em uma lista operacional limitada de portas para inspeção.

## 2. Papel de cada modelo

### 2.1 Modelo 7 — CatBoost

O [Modelo 7](/sprints/sprint-2/modelos/modelo-7) representa cada observação como uma combinação de estação, plataforma e dia. Uma PSD neste modelo corresponde ao sistema completo de portas de uma plataforma, e não a uma porta PDM individual.

Sua função no pipeline é:

1. calcular o risco de falha de cada plataforma;
2. aplicar o limiar operacional do CatBoost;
3. encaminhar ao Modelo 5 somente as plataformas classificadas como risco.

### 2.2 Modelo 5 — Random Forest

O [Modelo 5](/sprints/sprint-2/modelos/modelo-5) representa cada observação como uma porta e um dia. Sua previsão usa o histórico específico de alarmes e manutenções da porta.

Sua função no pipeline é:

1. receber as portas que pertencem às plataformas sinalizadas pelo Modelo 7;
2. calcular o risco individual de cada porta;
3. ordenar as portas para apoiar a priorização de inspeções.

## 3. Contrato de integração

A tabela a seguir registra o estado atual dos dois modelos. As diferenças marcadas como **ajuste obrigatório** devem ser resolvidas antes da implementação do pipeline.

| Item | Modelo 7 — CatBoost | Modelo 5 — Random Forest | Situação para integração |
|---|---|---|---|
| Ordem no pipeline | Primeiro | Segundo | Compatível |
| Granularidade | Estação × plataforma × dia | Porta × dia | Compatível, complementar e proposital |
| Cobertura | 22 sistemas: 11 estações × 2 plataformas | 480 portas de 10 estações | Ajuste obrigatório |
| Momento atual da previsão | Final do dia `D`; pode usar eventos ocorridos em `D` | Início do dia `D`; usa somente eventos anteriores a `D` | Ajuste obrigatório |
| Horizonte | De `D+1` a `D+7` | Implementado como `(D, D+7]` | Mesmo tamanho, mas depende do alinhamento do momento da previsão |
| Definição atual de falha | ZM01 com `falha_flag == True` em alguma porta da plataforma | Qualquer ordem ZM01 da porta | Ajuste obrigatório |
| Target | `target_falha_7d` | `y` | Os nomes podem diferir; a semântica deve ser igual |
| Chave da plataforma | `id_psd`, como `BUT_P1` | `id_plat`, como `BUT_1` | Conversão obrigatória |
| Chave da porta | Preservada nas fontes, mas não é a unidade prevista | `id_porta`, como `BUT_1_05` | Padronização obrigatória |
| Features | 21 features registradas no metadata | 71 features selecionadas por SHAP e congeladas no novo metadata | Cada modelo mantém seu próprio conjunto |
| Limiar registrado | `0,317380` | `0,488753` no artefato do pipeline | Manter limiares separados |
| Modelo serializado | `modelo_catboost.cbm` e `metadata_modelo.json` | `modelo_5_random_forest.joblib` e `metadata_modelo_5.json` | Compatível |

## 4. Data de referência e horizonte

O pipeline será iniciado ao **final do dia `D`**, seguindo a definição do Modelo 7. Assim:

```text
Informações permitidas: tudo o que estiver disponível até o final do dia D
Janela prevista: D+1, D+2, ..., D+7
```

Essa escolha permite que o Modelo 7 use as informações do próprio dia `D`, como foi treinado. O Modelo 5 foi construído com `shift(1)` e utiliza somente o histórico até `D-1`. Na primeira versão do pipeline, essa regra original será preservada: depois do alerta de plataforma, o Random Forest será executado com as features que ele já conhece e para as quais foi treinado.

Os dois modelos observam o mesmo horizonte futuro de sete dias, mas o Modelo 5 deixa de utilizar o dia mais recente. Isso não impede o encadeamento inicial; significa apenas que os dois scores usam quantidades de informação diferentes. Uma versão futura poderá retreinar o Modelo 5 para incluir os eventos de `D`, caso essa mudança melhore o desempenho em validação temporal.

Nenhuma feature poderá utilizar eventos posteriores ao final do dia `D`. O target também nunca poderá ser fornecido como entrada dos modelos.

## 5. Definição de falha em cada etapa

O objetivo de negócio do pipeline é antecipar uma falha de porta nos sete dias seguintes. Entretanto, os targets atuais não são idênticos:

- o Modelo 7 considera ZM01 com `falha_flag == True` em alguma porta da plataforma;
- o Modelo 5 considera qualquer ZM01 futura associada à porta.

Na primeira versão, cada modelo manterá a definição com a qual foi treinado. O Modelo 7 será interpretado como alerta de **falha confirmada na plataforma**, enquanto o Modelo 5 será interpretado como priorização da **porta com maior risco de receber uma corretiva**.

Essa diferença não impede o teste técnico do encadeamento, mas limita a interpretação da saída. Para avaliar futuramente o pipeline inteiro contra um único target de falha confirmada, será necessário alterar o target do Modelo 5, retreiná-lo e comparar o resultado com sua versão original.

## 6. Padronização das chaves

O contrato define as seguintes chaves canônicas para o pipeline:

| Chave | Formato | Exemplo |
|---|---|---|
| Estação | Código de três letras | `BUT` |
| Plataforma | Número inteiro | `1` |
| PSD | `{ESTACAO}_P{PLATAFORMA}` | `BUT_P1` |
| Porta | `{ESTACAO}_P{PLATAFORMA}_PDM{PORTA:02d}` | `BUT_P1_PDM05` |

Os identificadores originais continuam podendo existir dentro de cada modelo, mas devem ser convertidos na fronteira do pipeline:

```text
Modelo 7: BUT_P1
Modelo 5: BUT_1 e BUT_1_05
Pipeline: BUT_P1 e BUT_P1_PDM05
```

A relação entre plataforma e portas deverá ser validada antes da inferência. Uma porta só pode ser enviada ao Modelo 5 quando sua estação e sua plataforma forem iguais às da plataforma alertada pelo Modelo 7.

## 7. Cobertura dos sistemas

O Modelo 7 contém 11 estações e 22 plataformas. O painel atual do Modelo 5 contém 10 estações e 480 portas; a estação `FRE` não aparece nesse painel.

Até que o Modelo 5 seja reconstruído com a mesma cobertura, o pipeline deverá seguir esta regra:

- plataformas com portas conhecidas pelo Modelo 5 seguem para a segunda etapa;
- uma plataforma de `FRE` alertada pelo Modelo 7 não pode ser descartada silenciosamente;
- nesse caso, o resultado deve permanecer como **alerta em nível de plataforma, sem detalhamento por porta**.

## 9. Limiar e regra de encaminhamento

Os limiares pertencem aos modelos e não devem ser confundidos:

```text
Modelo 7: probabilidade >= 0,317380 → plataforma alertada
Modelo 5: probabilidade >= 0,488753 → porta alertada
```

O valor `0,5183` foi o limiar do experimento executado na Sprint 2. Como aquele objeto treinado não havia sido salvo, a Task 2 reconstruiu o modelo e selecionou novamente o limiar na validação, resultando em `0,488753`. O teste não participou dessa escolha.

Somente as portas de plataformas alertadas pelo Modelo 7 serão avaliadas pelo Modelo 5. Uma plataforma abaixo do limiar encerra o fluxo naquela data. Dessa forma, o CatBoost ajuda o Random Forest ao restringir o conjunto de portas que precisam ser analisadas.

O score do Modelo 7 não será adicionado diretamente às features do Modelo 5 nesta primeira versão, porque o Random Forest não foi treinado com essa variável. A ajuda ocorre pelo **filtro hierárquico**. Uma porta será priorizada quando pertencer a uma plataforma alertada e também atingir o limiar do Modelo 5.

## 11. Resultado da análise de compatibilidade

Os modelos são **conceitualmente complementares e podem formar o pipeline proposto**. O Modelo 7 responde “em qual plataforma existe risco?” e o Modelo 5 responde “qual porta dessa plataforma deve ser priorizada?”. A granularidade diferente é justamente o mecanismo pelo qual um modelo ajuda o outro.

O contrato e a preparação do Modelo 5 já concluíram:

1. a definição do encadeamento Modelo 7 → Modelo 5;
2. o congelamento das 71 features do Modelo 5, sua ordem, seus tipos e seu novo limiar;
3. a serialização do Random Forest e a criação de seu metadata.

Também foram concluídos na Task 3:

1. a conversão das chaves entre os dois modelos;
2. o mapeamento das 480 portas para as 20 plataformas cobertas pelo Modelo 5;
3. o tratamento explícito das plataformas e datas sem cobertura;
4. a materialização da saída intermediária do Modelo 7.

Na Task 4, foram concluídas a inferência do Modelo 5 sobre as portas encaminhadas, a priorização das portas e a comparação do pipeline completo com o Random Forest isolado.

Na Task 5, o pipeline passou a reconstruir as 21 features do Modelo 7 a partir da tabela mestra diária e a executar o CatBoost salvo antes de encaminhar as portas ao Modelo 5.

Na Task 6, a execução passou a reutilizar os modelos por padrão, com avaliação histórica opcional e um relatório que preserva todas as plataformas previstas, inclusive as que não puderam ser detalhadas por porta.

O alinhamento do target e do uso do dia `D` no Modelo 5 fica registrado como aprimoramento metodológico posterior. Ele será necessário caso o grupo queira avaliar os dois estágios como um único modelo com exatamente o mesmo target, mas não impede a construção do primeiro pipeline sequencial.

Com essas condições atendidas, o fluxo acordado será:

```text
Modelo 7 — CatBoost por plataforma
              ↓ somente plataformas alertadas
Modelo 5 — Random Forest por porta
```

## 12. Task 2 — Preparação do Modelo 5 para inferência

O notebook novo `models/pipeline-sequencial/pipeline_sequencial_modelos_7_5.ipynb` reconstruiu o Modelo 5 exclusivamente a partir das bases existentes. Essa reconstrução continua disponível com `RETREINAR_MODELO_5 = True`; o padrão atual é reutilizar o artefato salvo. Nenhum notebook, dado ou documento das sprints anteriores foi alterado.

O processo realizado foi:

1. carregar o painel diário já construído pelo Modelo 5;
2. reproduzir as features adicionais criadas no notebook original;
3. manter as mesmas 71 features selecionadas após a análise SHAP;
4. respeitar a divisão temporal original entre treino, validação e teste;
5. selecionar o limiar pela maior F1 na validação;
6. treinar o Random Forest final e salvar o modelo e seu contrato de entrada.

Os arquivos produzidos ficam isolados em `models/pipeline-sequencial/artefatos/`:

- `modelo_5_random_forest.joblib`: Random Forest treinado;
- `metadata_modelo_5.json`: features, tipos, ordem, limiar, hiperparâmetros, períodos e métricas.

No teste temporal, o artefato obteve **14,51% de precisão**, **63,50% de recall**, **23,63% de F1**, **18,53% de PR-AUC** e **69,68% de ROC-AUC**. O modelo gerou 27.131 alertas, com 3.938 verdadeiros positivos e 2.264 falhas não detectadas.

Por fim, o artefato foi recarregado do disco e suas probabilidades foram comparadas às produzidas antes da gravação. Os valores foram iguais, confirmando que o modelo pode ser carregado posteriormente pelo pipeline sem mudança nas previsões.

## 13. Task 3 — Padronização das chaves e encaminhamento

A Task 3 implementou a fronteira entre o nível de plataforma e o nível de porta. As chaves internas do Modelo 5 foram convertidas para o padrão canônico definido pelo contrato:

```text
BUT_1    → BUT_P1
BUT_1_05 → BUT_P1_PDM05
```

O mapa resultante contém **480 portas**, distribuídas igualmente entre **20 plataformas**, com 24 portas por plataforma. As duas plataformas de `FRE` presentes no Modelo 7 não possuem portas no painel do Modelo 5 e permanecem identificadas como alertas sem detalhamento.

Além da cobertura por plataforma, foi verificada a disponibilidade das features para cada combinação exata de plataforma e data. O período padrão de execução do Modelo 7 vai de **01/10/2025 a 21/03/2026**, enquanto o painel disponível do Modelo 5 termina globalmente em **31/10/2025** e algumas plataformas deixam de aparecer antes dessa data. Portanto, o período global, sozinho, não é considerado evidência suficiente de cobertura.

O pipeline utiliza os seguintes status:

| Status | Significado |
|---|---|
| `sem_alerta_modelo_7` | A plataforma não atingiu o limiar do CatBoost |
| `alerta_sem_mapeamento_portas` | Existe alerta, mas não há portas dessa plataforma no Modelo 5 |
| `alerta_sem_features_modelo_5` | Existe alerta e mapeamento, mas não há features para a plataforma naquela data |
| `encaminhar_modelo_5_cobertura_parcial` | Apenas parte das portas possui features; somente as disponíveis são encaminhadas |
| `encaminhar_modelo_5` | O alerta possui plataforma e data cobertas |

Foram encontrados **406 pares de plataforma e data elegíveis**, que correspondem a **9.744 linhas de porta** encaminhadas. Também ficaram registrados 344 alertas sem mapeamento de portas, 2.543 alertas sem features na combinação exata de plataforma e data e 491 casos sem alerta do Modelo 7. Na base atual, todos os 406 pares elegíveis possuem as 24 portas; nenhum caso de cobertura parcial ocorreu, mas a regra ficou implementada para dados futuros.

Os arquivos gerados em `models/pipeline-sequencial/artefatos/` são:

- `mapa_chaves_portas.csv`: relação entre as chaves internas e canônicas;
- `saida_intermediaria_modelo_7.csv`: resultados de plataforma e status de encaminhamento;
- `portas_encaminhadas_modelo_5.csv`: portas elegíveis para a próxima inferência;
- `metadata_integracao_chaves.json`: formatos, coberturas, períodos e contagens de auditoria.

Essa etapa não calcula o score das portas. Ela prepara e valida exatamente quais linhas podem ser avaliadas pelo Random Forest na Task 4.

## 14. Task 4 — Inferência e priorização das portas

A Task 4 carregou o Random Forest serializado e o executou somente sobre as **9.744 portas encaminhadas**. Para cada porta, foram produzidos:

- a probabilidade calculada pelo Modelo 5;
- a decisão pelo limiar `0,488753`;
- a posição no ranking de risco da plataforma;
- uma marcação para a porta de maior risco em cada plataforma e data.

O pipeline produziu **5.013 alertas de porta/dia** em 406 pares de plataforma e data. Uma mesma porta pode aparecer em diferentes dias. Todas as plataformas encaminhadas tiveram ao menos uma porta acima do limiar. Como o limiar permite múltiplos alertas, a quantidade média foi de aproximadamente 12 portas priorizadas por plataforma e data; o ranking permite selecionar primeiro a porta com maior score.

### 14.1 Avaliação no período comum

A comparação foi feita entre **01/10/2025 e 31/10/2025**, usando somente as 11.904 linhas em que existem previsões do Modelo 7 e features do Modelo 5. Para medir o efeito do encadeamento, foram comparados o Random Forest isolado e a decisão final que exige alerta dos dois modelos.

| Cenário | Precisão | Recall | F1 | PR-AUC | ROC-AUC | Alertas |
|---|---:|---:|---:|---:|---:|---:|
| Modelo 5 isolado | 10,93% | 66,82% | 18,79% | 13,57% | 65,20% | 5.415 |
| Pipeline Modelo 7 → Modelo 5 | 11,05% | 62,53% | 18,78% | 13,59% | 63,78% | 5.013 |

O filtro do Modelo 7 reduziu em **18,15%** a quantidade de portas enviadas ao Random Forest e em **7,42%** os alertas finais. Entretanto, a precisão aumentou apenas 0,12 ponto percentual, o recall caiu 4,29 pontos percentuais e o F1 permaneceu praticamente igual, com uma pequena redução.

Portanto, esta primeira versão comprova que o encadeamento técnico funciona e reduz o volume processado, mas **não demonstrou melhora da qualidade preditiva**. Antes de uso operacional, os modelos devem ser alinhados para o mesmo target, avaliados em um período comum maior e ter seus limiares ajustados em conjunto.

## 15. Task 5 — Preparação e inferência direta do CatBoost

O notebook agora lê `data/processados/modelo-7/tabela_mestra_psd.csv`, reconstrói as 21 features e carrega `models/modelo-7/modelo_catboost.cbm`. As previsões resultantes alimentam as Tasks 3 e 4. Por essa dependência, o bloco da Task 5 aparece **antes da Task 3** no notebook.

### 15.1 Preparação das entradas

Foram reproduzidas as regras do notebook de processamento do Modelo 7:

- contagens e durações diárias, com janelas de alarmes de 7 dias;
- contagens de manutenção em 30 dias;
- tempo desde a última corretiva e preventiva, incluindo os eventos de D;
- dia da semana e demais categorias com a representação e a ordem esperadas pelo artefato.

As features usam informações disponíveis até o final de D. O target e as contagens futuras não participam dessa preparação. Quando nenhuma manutenção anterior foi observada, a recência permanece ausente, como no treinamento original. Datas duplicadas, lacunas no calendário, chaves inconsistentes e histórico insuficiente interrompem a preparação com uma mensagem de erro.

### 15.2 Execução e conferência

As variáveis `INICIO_INFERENCIA_MODELO_7` e `FIM_INFERENCIA_MODELO_7` definem o período. O padrão mantém **01/10/2025 a 21/03/2026**, para comparação com o teste histórico. O horizonte continua em **7 dias** e o limiar é lido do metadata do CatBoost (`0,31738017595573687`).

Nesse período, foram calculadas **3.784 previsões de plataforma/dia**, sendo **3.293 alertas**. As 21 features foram comparadas à base de teste original, e as probabilidades ao CSV histórico: a maior diferença foi inferior a `1e-12`, com todas as decisões iguais. Os resultados finais das Tasks 3 e 4 também foram preservados: 9.744 registros de porta/dia avaliados, 5.013 alertas finais, precisão de 11,05% e recall de 62,53%.

Também foi verificado que uma previsão para D permanece igual quando todos os registros posteriores a D são removidos. A rotina conseguiu prever no último dia disponível da tabela mestra sem precisar de sete dias futuros nem do target. Entradas com duplicatas, dias ausentes, colunas faltantes e menos de 30 dias de histórico foram rejeitadas nos testes.

### 15.3 Artefatos e uso

Dois arquivos foram acrescentados a `models/pipeline-sequencial/artefatos/`:

- `previsoes_modelo_7_pipeline.csv`: previsões calculadas pelo CatBoost, sem target;
- `metadata_execucao_modelo_7.json`: período, features, limiar, versão do CatBoost e hashes dos arquivos de entrada e do modelo, para identificar a execução.

Para executar, use o kernel com `catboost==1.2.10` instalado, ajuste a configuração inicial e execute as células em ordem. Desde a Task 6, `RETREINAR_MODELO_5 = False` é o padrão: as células de treino e exportação da Task 2 são ignoradas, e o pipeline carrega o Random Forest salvo.

Esta etapa parte da **tabela mestra diária já agregada**. Para operar em datas novas, ainda é necessário atualizar essa tabela e o painel de features do Modelo 5 com os dados do parceiro. ### 16.1 Casos sem detalhamento ou sem target

Quando nenhuma porta é encaminhada, o pipeline exporta a saída de portas vazia, com os cabeçalhos, e preserva os resultados de plataforma. O Random Forest não é chamado com uma entrada vazia. Quando apenas parte das portas possui features, somente essas portas são avaliadas, e a cobertura parcial fica identificada.

O target `y` foi retirado da preparação das entradas de inferência e é associado às previsões apenas na avaliação. A execução sem target continua produzindo alertas. A avaliação registra um dos estados: `concluida`, `desativada`, `sem_target`, `target_incompleto` ou `sem_periodo_comum`. Métricas não calculadas são gravadas como `null`, e não como um desempenho igual a zero.

### 16.2 Relatório da execução

Dois arquivos complementam os resultados anteriores:

- `status_plataformas_pipeline.csv`: contém todas as plataformas e datas previstas, incluindo ausência de alerta, falta de cobertura, cobertura parcial e plataformas com portas priorizadas;
- `resumo_execucao_pipeline.json`: registra configuração, identificação dos modelos, limiares, contagens e situação da avaliação.

No relatório de plataformas, uma quantidade vazia de portas priorizadas significa que o Modelo 5 não foi executado para aquele caso. O valor zero significa que as portas foram avaliadas, mas nenhuma atingiu o limiar. Essa distinção evita interpretar ausência de dados como ausência de risco.

As contagens distinguem **alertas de porta/dia** de **portas distintas**, pois uma mesma porta pode ser alertada em vários dias. O relatório de avaliação é atualizado em cada execução, mesmo quando as métricas não puderem ser calculadas.

Foram testados o período histórico completo, uma data sem cobertura do Random Forest, nenhuma plataforma alertada, nenhuma porta acima do limiar, inferência sem target, avaliação solicitada sem target, target incompleto e cobertura parcial de portas. A precisão permaneceu em 11,05% e o recall em 62,53%. A Task 6 melhora a execução e a rastreabilidade; não altera o modelo nem suas métricas.

## 17. Task 7 — Lista operacional de manutenção

A saída `saida_final_portas_priorizadas.csv` é mantida como resultado analítico completo: ela contém todas as portas que superaram o limiar do Modelo 5. Como esse arquivo gera em média aproximadamente 12 alertas por plataforma e data, ele não deve ser confundido com uma lista curta de inspeção.

A Task 7 gera `recomendacoes_manutencao.csv`. Por padrão, o arquivo mantém somente a porta de maior probabilidade entre as que passaram pelos dois modelos em cada plataforma e data. Cada linha informa a data de referência, o intervalo futuro de `D+1` a `D+7`, a plataforma, a porta, os dois scores e a posição no ranking. O limite pode ser alterado na configuração sem modificar os artefatos dos modelos.

No período comum de teste, a configuração de uma porta por plataforma gerou **406 recomendações de porta/dia**. A precisão subiu para **20,20%**, enquanto o recall caiu para **9,26%**. Essa redução do recall é esperada porque a lista operacional aceita apenas uma porta por plataforma. Portanto:

- a saída completa deve ser usada para avaliação e análise dos alertas;
- a lista operacional deve ser usada quando a capacidade de inspeção exige uma recomendação curta;
- aumentar o limite de portas amplia a cobertura, mas também aumenta a quantidade de inspeções.

A lista operacional não representa um terceiro modelo e não altera os limiares. Ela é apenas uma regra de priorização aplicada ao ranking já produzido pelo Random Forest.
