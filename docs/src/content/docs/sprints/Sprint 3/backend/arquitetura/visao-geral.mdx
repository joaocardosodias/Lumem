A arquitetura do backend foi concebida e implementada para suportar a operação contínua e a predição de falhas em portas de plataforma (PSD) da Linha 4-Amarela do Metrô de São Paulo. A solução desacopla o processamento de requisições web da execução de tarefas analíticas pesadas, garantindo que reinicializações ou picos de carga não degradem a experiência dos operadores nas estações.

Esta página detalha a topologia do sistema utilizando o modelo **C4 (Context, Containers, Components)**, descrevendo as fronteiras de rede, os protocolos de comunicação e as garantias de disponibilidade.

## 1. Nível C4 — Contexto do sistema

O backend atua como o núcleo operacional e preditivo da plataforma. Ele integra operadores, interface web, modelo de inteligência artificial, PostgreSQL gerenciado no Supabase e serviços autocontidos na VPS.

### Atores e integrações externas

1. **Operador de Linha e Manutenção:** visualiza no frontend o status preditivo das portas em cada estação (ex: Luz, Paulista, Pinheiros) e cadastra ordens de inspeção preventiva ou corretiva;
2. **Engenheiro de Dados:** realiza o upload das planilhas brutas de telemetria extraídas dos sistemas do metrô (ZM01 - Corretivas, ZM02 - Preventivas e ZM03 - Alarmes de Portas);
3. **Supabase PostgreSQL 16:** banco gerenciado que armazena entidades de domínio, usuários, inspeções, predições históricas e as tabelas da fila River;
4. **MinIO:** servidor S3 autocontido com buckets privados para ingestões, datasets de treinamento e artefatos de modelos;
5. **Microsserviço de Machine Learning:** serviço Python executado na mesma VPS que treina versões e retorna probabilidades de falha.

## 2. Nível C4 — Contêineres e topologia de rede

A infraestrutura é executada em contêineres Docker interligados pela rede interna isolada `backend-network`. O proxy reverso Nginx atua como único ponto de entrada para o tráfego HTTP vindo da internet.

### Especificação dos contêineres em execução

| Contêiner | Papel técnico | Porta interna | Exposta no host | Política de persistência |
|---|---|---:|:---:|---|
| `nginx` | Proxy reverso, terminação de conexões e roteamento de subpaths | 80 | Sim (80) | Sem estado local |
| `backend-linha4` | API HTTP em Go: autenticação, recepção de uploads e agendamento de jobs | 8080 | Não | Sem estado próprio (stateless) |
| `worker-linha4` | Processador assíncrono em Go: polling do River, leitura S3 e batch SQL | — | Não | Sem estado próprio (stateless) |
| `otel-collector` | Agregador OpenTelemetry: recebe OTLP gRPC/HTTP e distribui para Tempo | 4317/4318 | Não | Buffer em memória de lote |
| `tempo` | Mecanismo de armazenamento de traces distribuídos | 3200 | Não | Volume Docker `tempo-data` |
| `prometheus` | Banco de séries temporais para métricas de infraestrutura e aplicação | 9090 | Não | Volume Docker `prometheus-data` |
| `loki` | Indexador e agregador de logs estruturados JSON | 3100 | Não | Volume Docker `loki-data` |
| `promtail` | Agente coletor de logs do socket Docker (`/var/run/docker.sock`) | — | Não | Arquivo de posições de leitura |
| `grafana` | Portal único de visualização de métricas, logs e traces | 3000 | Não | Volume Docker `grafana-data` |

### Imagem única para API e Worker

Tanto o contêiner `backend-linha4` quanto o `worker-linha4` são instanciados a partir da **mesma imagem Docker** compilada no pipeline. A imagem contém dois binários estáticos: `/app/api` e `/app/worker`.
- A API inicia executando `/app/api` (padrão do `ENTRYPOINT`);
- O Worker substitui o comando no Compose por `command: ["/app/worker"]`.

Essa abordagem elimina divergências de versões de bibliotecas e modelos de dados entre quem produz o job e quem o consome.

## 3. Nível C4 — Componentes internos do backend

Dentro da base de código em Go, os componentes são estruturados segundo as camadas da Clean Architecture:

```text
src/backend/
├── cmd/
│   ├── api/          -> Composition Root da API HTTP (instancia adaptadores e inicia Gin)
│   └── worker/       -> Composition Root do Worker (instancia processadores e registra no River)
├── internal/
│   ├── domain/       -> Entidades com invariantes (Alarm, Inspection, Maintenance, Upload)
│   ├── usecase/      -> Orquestração de negócio (IngestAlarms, IngestMaintenance, Login, etc.)
│   │   └── port/     -> Interfaces desacopladas (Repositories, Storage, JobQueue, MLClient)
│   └── adapter/      -> Implementações concretas de infraestrutura
│       ├── http/     -> Handlers Gin, middlewares, DTOs e Problem Details
│       ├── repository/ -> Repositórios PostgreSQL parametrizados e Unit of Work
│       ├── storage/  -> S3Storage e LocalTempStorage
│       ├── jobqueue/ -> RiverQueue e IngestionWorker
│       ├── mlclient/ -> Cliente HTTP com Circuit Breaker para o serviço Python
│       └── telemetry/-> Configuração do TracerProvider OpenTelemetry OTLP
```

Os composition roots em `cmd/api/main.go` e `cmd/worker/main.go` são os únicos pontos onde structs concretas encontram as interfaces.

### Controles de segurança aplicados

1. **Buckets S3 estritamente privados:** o MinIO bloqueia acesso anônimo e aceita operações dos contêineres pela conta técnica limitada pela política `g04-app`;
2. **Defesa contra injeção SQL:** todos os repositórios utilizam consultas preparadas parametrizadas (`$1, $2, ...`), impedindo injeção mesmo em consultas complexas;
3. **Bloqueio de métricas externas:** a rota `/metrics` do Prometheus é bloqueada pelo Nginx para clientes de fora da rede interna;
4. **Proteção contra sobrescrita:** arquivos enviados geram nomes compostos por UUID v4 e prefixo controlado, impossibilitando path traversal ou substituição acidental de arquivos de outro operador.

## 5. Características de disponibilidade e tolerância a falhas

1. **Desacoplamento do ciclo de vida:** a API não depende da conclusão do parsing para liberar a conexão HTTP do operador. Se o contêiner `worker-linha4` for reiniciado durante um deploy, os jobs persistem no PostgreSQL e são retomados do ponto onde pararam;
2. **Consumo previsível da fila:** o River permanece com `RIVER_POLL_ONLY=true`, realizando consultas periódicas e evitando conexões de notificação duradouras. Essa configuração facilita observar e limitar o consumo de recursos na VPS;
3. **Escalabilidade independente:** caso o volume de planilhas aumente em dias de manutenção pesada, é possível escalar o número de réplicas do contêiner `worker` sem precisar alterar o número de instâncias da API HTTP.
